## P0 · 跨对象写队列错位会导致盲签（唯一的严重缺陷）

这是 0028 整条设计要防的失败模式，现在以另一种形式出现了。

**复现**（种子态起）：

1. 打开周若水，在对话里说「把这份 JD 绑到栈桥科技」→ 提议入队，不确认。
2. 切到栈桥科技，说同一句 → 第二条提议入队。
3. 栈桥科技页面的 takeover 显示「把 jd-zhanqiao.txt 绑到当前对象」，**没有**「还有 n 条待确认」。
4. 点确认 → 应用跳到周若水，JD 绑到了周若水。

**成因是两处叠加**：

- `components/Takeover.tsx` 显示的是 `state.writeQueue.filter(w => w.objectId === objectId)[0]`，而 `store.tsx` 的 `CONFIRM_WRITE` / `REJECT_WRITE` 操作的是全局 `state.writeQueue[0]`。两套「队首」定义。「还有 n 条」也按过滤后计数，所以队列里属于别的对象的提议完全不提示。
- `chat.ts` 的绑定提议 `draft.objectId` 取当前对话对象，**完全无视句子里指名的对象**，headline 却写「绑到当前对象」。用户说的是「绑到栈桥科技」，在周若水页面说就会绑到周若水。

**后果比绑错对象更深**：`pendingClaims` 的 objectId 是硬编码的 `org-zhanqiao`，于是主张落在栈桥科技而来源绑在周若水——栈桥科技档案里有 4 条主张，它们的来源不在栈桥的「来源」标签里，审计链断了。

### 做法

**P0-1a 确认与拒绝必须指名提议。** `CONFIRM_WRITE` / `REJECT_WRITE` 带 `writeId`，由 Takeover 把它正在显示的那条 id 传进来；reducer 按 id 找，找不到就什么都不做（不要退化成取队首）。这是 0028 那句「显示哪条与执行哪条必须是同一条」的落法。

**P0-1b 队列跨对象时要看得见。** takeover 只显示当前对象的队首没问题，但计数要分开写：「本对象还有 n 条」与「其他对象还有 m 条」。其他对象那部分给一个可点的入口（点了切到那个对象并显示它的队首），不要让提议悄悄堆在看不见的地方。

**P0-1c 提议的对象归属由句子决定。** `chat.ts` 的绑定分支要从句子里解析对象名（种子里就是「栈桥科技 / 后端实习 2026 秋招 / 周若水」这三个名字，做字符串包含匹配即可），解析到就用那个对象；解析不到**不产提议**，回一句「你要绑到哪个对象？说出名字」。不许默默用当前对话对象顶替。同时 headline 改成写死具体对象名（「把「jd-zhanqiao.txt」绑到「栈桥科技」」），不要再出现「当前对象」这种含糊措辞——确认卡上的每个名词都必须是确定的。

**P0-1d 顺手补一致性检查。** `BIND_CONFIRMED` 落地时，如果 `pendingClaims` 里该来源的主张 objectId 与本次绑定的对象集合不相交，说明种子与绑定对象不匹配：抽取结果卡要写清「主张挂在 X，本次绑定的是 Y」，而不是静默让两者分家。原型里这属于种子约束，但这条检查是真实实现也需要的（0024 的幂等键是「来源片段 + 对象 + 谓词槽」，对象错了幂等键就错了）。

## P1 · 结果卡改回单行，顺手收三处视觉

refit-2 的 P1 写的是「结果卡 = 只读一行摘要 + 可点回引用」，实际做成了与审计卡同规格的 20px 圆角全宽卡。绑定加抽取一次就是三张大卡叠起来占掉半屏，每张只有一句话。这是主人说的「丑」在这一轮的主要残留：不是配色，是信息密度。

**P1-1 结果卡降级为单行。** 照 DSH 的 `ToolRow` / `MessageItem` 里 compaction row 的做法（`ui-tool/.../ToolRow.module.css`、`ui-chat/.../MessageItem.module.css`）：24px 单行、`[16px leading 图标] gap6 [文本 13/24] gap8 [可点引用]`，hover 才出底色（`--hover`），无边框、无阴影、无 kicker。四种结果（关窗 / 晋升 / 记忆 / 简报 / 绑定 / 抽取）用不同的 leading 图标区分，不要用「结果」两个字重复六遍。

**P1-2 「打开主张」「打开简报」进 `.btn` 体系。** 现在是蓝色下划线 link 混在 `.deal-actions` 里。单行化之后它应该是行尾的 `ref-chip` 或 `.btn ghost sm`，二选一，不要第三种样式。

**P1-3 工具行的完成点收回文本旁。** 现在 done 的绿点飘到内容轴（680px）最右端，离 summary 很远，看着像随机噪点。DSH 的做法是 summary 用 `flex: 1 1 auto` + `text-overflow: ellipsis`，状态点紧跟其后。照改。

**P1-4 抽取结果卡的「打开主张」要么全给要么不给。** 现在写「抽出 3 条主张」但只能打开一条（`card.claimId` 只存了一个）。改成列出 3 个 `ref-chip`，或者干脆不给按钮、让人去右栏档案看。**不要**保留「说 3 条只能点开 1 条」这种状态。

## P2 · 收敛没做完的尾巴

**P2-1 字号还有 12px 22 处。** refit-2 要求收到 15/14/13/11 四档，实测仍有 12px 共 22 处。逐处判断该升到 13 还是降到 11。（h1 的 20px 是标题层，refit-2 的清单里漏写了，保留，不算问题。）

**P2-2 删死代码。** `components/cards/CorrectCard.tsx` 已经没有任何引用（纠正搬进了 takeover），`types.ts` 的 `ChatCardKind` 里 `'纠正'` 也没有入口了。两个都删掉。仓库里不留没有入口的组件。

**P2-3 thinkCopy 与实际动作对齐。** `turn.ts` 的 `thinkCopy` 只看 `claimRefs` 和 `note`，所以绑定提议那一轮会显示「账本无匹配，按未知处理」，紧接着弹出绑定确认——说的和做的不一致。给它一个「本轮要提议什么」的输入（`ChatReply.effect` 的种类就够），提议类的思考行写「要动账本，等你确认」。

**P2-4 窄窗时主栏优先。** 1100px 窗口下主栏被挤到 385px 而右栏仍占 400px，跟 0027「主栏成交」的优先级相反。给 `.chat-pane` 一个 `min-width`（建议 420px），或者主栏低于阈值时自动收起右栏（保留手动展开）。二选一，写清选了哪个。

**P2-5 禁写拦截补上整理。** `enqueueWrite` 里的 `bannedHit` 只覆盖「晋升」和「纠正」。一条命中禁写但仍活着的主张，走「整理并入受控槽」之后仍可能出站。整理分支也过一遍。
