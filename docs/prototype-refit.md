## P0 · 三处硬伤（行为错了，不修会被下一刀照抄）

### P0-1 冲突从未登记

**根因。** `seed.ts` 的 `makeInitialState` 写死 `conflicts: []`。reducer 除 `DELETE_OBJECT` 过滤已删对象上的对外，没有任何 action 往 `conflicts` 里 push。`EXTRACT_DONE` 只是把 `pendingClaims` 原样拼进 `claims`。`store.tsx` 顶部注释声称「种子预置 Go/Java 一对」，注释是假的。`ObjectPage` 的 `conflict-box`、`ClaimDrawer` 的冲突段、`brief.ts` 的 `conflictPairs` 全读 `state.conflicts`，于是 Go / Java 两条只是同槽上下两张卡。`chat.ts` 在 `tech.length >= 2` 时口头说「两条互斥主张并排」，并不查 `Conflict[]`，把洞盖住了。`docs/prototype.md` 验收第 5 条过不了；0003 在界面上没有任何证据。

**做法（原型层最小正确做法，手工登记，不要发明判定器）。**

- `seed.ts` 导出 `seedConflicts: Conflict[] = [{ claimIdA: 'cl-2', claimIdB: 'cl-3' }]`。`EXTRACT_DONE` 在两条都已入账时把这一对写入 `conflicts`（幂等：已有则不重复）。登记放 reducer，不要放组件。
- `PROPOSAL_DECIDE` 的 `accept-merge` 把未编目并入受控槽之后，同槽内按已入账主张重新套用预置对；现在并进「使用技术」也不会补冲突。
- 判定条件仍按 CONTEXT：同一对象 + 同一受控谓词 + 有效期重叠 + 取值互斥。前三条可以按字段算。**「取值互斥」由谁判是待拍板 §1，原型继续用预置对。**

**验收。** 绑定抽取完成后，档案「使用技术」出现冲突框、两条并排；简报技术信号块两句都带「冲突·并排」。未编目那条始终不进 `conflicts`。

### P0-2 官网摘录来源是残缺空对象

**根因。** `BIND_CONFIRMED` 在绑 `src-jd` 时想内置官网摘录：

```ts
const { sources: seedSources } = makeInitialState();
const web = seedSources.find((s) => s.id === 'src-web')!;
sources = [...sources, { ...web, boundObjectIds: [orgId] }];
```

`makeInitialState` 自己已经 `sources.filter((s) => s.id !== 'src-web')`，所以 `find` 运行时一定是 `undefined`。`Array.prototype.find` 的类型是 `T | undefined`；后缀 `!` 是非空断言，告诉 tsc「我保证不是 undefined」，于是 `web` 被当成 `Source`。tsc 不执行 `filter`，看不到断言是假的，`--noEmit` 放行。运行时 `{ ...undefined, boundObjectIds }` 在 JS 里等价于 `{ boundObjectIds }`（对 undefined 做 spread 是 no-op），于是账本里多一条没有 `id` / `title` / `body` / `path` 的残缺对象。抽取仍靠 `pendingClaims` 里写死的 `sourceId: 'src-web'` 把 `cl-2` 入账，所以主张在、来源卡是空的。

连带可见故障：来源栏一张无标题卡；`cl-2` 审计里进料路径空白、来源「—」、没有原文片段；档案标签露出裸 id `src-web`；整个原型从未出现过「调研」这条进料路径，0004 的手给 vs 调研对照没被演示。

**做法。** `seed.ts` 同时导出完整 `allSources`（含 `src-web`）和「初始可见集合」（滤掉 `src-web`）。`BIND_CONFIRMED` 从完整集合取。去掉 `!`：找不到就 `return` 当前累积状态，不要 spread。不要再调用 `makeInitialState()` 当查找表。

**验收。** 绑定后来源栏两张卡，第二张标题是官网摘录、标签「调研」；打开 `cl-2` 能看到进料路径 = 调研 · 主键，以及原文片段。

### P0-3 候选记忆是死按钮

**根因。** `PendingView.tsx` 候选记忆的「接受 · 并入耐久记忆」「驳回」没有 `onClick`。更深一层：`Proposal.payload` 类型是 `{ claimId: string; targetPredicate: Predicate }`，候选记忆无法建模；列表还用 `claimId → object → workspace` 过滤，种子又没有 `type: '候选记忆'` 的提议，于是 0022 的候选链覆盖为零。

**`prototype.md` 自己有三处口径打架：**

1. **范围第 8 项 / 待确认节：** 两段都做；每条接受 / 驳回，接受才改账本或记忆。
2. **主链「对话补充」：** 「记下来：简报用条目」→ 立刻一条全局记忆（**或进候选，二选一**：明确「记下来」走立刻写）。
3. **验收第 12 条：** 整理提议接受/驳回会改账本；候选记忆接受/驳回会改记忆（禁止死按钮）。

**以 1 + 3 为准：两段都做、都能点。** 「记下来」立刻写耐久记忆，不走候选（0022）；候选记忆是另一条路——会话扫出的偏好，等人确认才升。主链那句「或进候选，二选一」删掉，避免执行者做成互斥。

**做法。**

- `Proposal.payload` 改成可辨识联合：整理是 `{ kind: '整理'; claimId: string; targetPredicate: Predicate }`，候选记忆是 `{ kind: '候选记忆'; text: string; memoryKind: MemoryKind; fromObjectId?: string }`。
- 接受候选 → 写一条耐久记忆（scope 默认全局）；驳回 → `pending: false, decision: 'reject'`，不写记忆。
- 种子预置一条候选记忆，文案是会话扫出的偏好，不要放世界事实。
- 过滤分开：整理按 claim 所属对象的工作区；候选按 `fromObjectId`，无则始终显示。

**验收。** 待确认两段都有内容；整理的并入 / 丢弃 / 驳回、候选的接受 / 驳回，四类按钮都改状态。接受后全局记忆多一条；驳回不写记忆。

## P1 · 形态重构：右栏只读，主栏成交

### 为什么改（两条必须写进 0027 的论据）

现在所有改账本、改记忆的动作都发生在对话之外：绑定确认在 Inbox，晋升和纠正在抽屉，整理提议在待确认页。对话仅有的两个写入口里，「这句不对」也只是去打开抽屉表单。主栏是只读解说器，不承载决策。

**这不是 ADR 写错，是执行偏离。** 0015 说的是「写入要经过明确指令」（闲聊不入库；纠正 / 「记下来」才写）。0021 说的是「对话默认只读，『记下来 / 这句不对』才打写入」。二者都没有说「写入在别处」。实现把写入搬到抽屉和右栏，主栏就被闲置。右栏承载全部操作之后，0026 拒掉的「CRM 三栏 = 记录浏览器」换了个位置回来，只是从三栏挤成「窄主栏 + 操作右栏」。

**冲突并排归主栏，是尺寸账，不是口味。** `.conflict-pair` 是 `grid-template-columns: 1fr 1fr`，嵌在 `minmax(320px, 1fr)` 的 `.slot-card` 里。右栏默认 400px（`App.tsx` `RIGHT_DEFAULT`，可拖 280–560）。扣掉卡片 padding、冲突框 padding 和列间隙，每侧大约 175px。一句「栈桥科技后端主栈是 Go。」要折三四行。冲突摊开双方是这个产品的招牌能力（0003），它在右栏宽度里排不下，本来就该在主栏。

### 原则

任何会改账本或记忆的动作，都在对话流里发生并确认。右栏退回纯投影。这是 0001「对象页是主张的投影」的原意。

`ClaimDrawer` 删除。它是应用里唯一的阅读态模态（`position: fixed` + 遮罩），盖住的正是要对照的那一槽，也是控件语言不统一的根源。

Inbox 的绑定确认留在 Inbox：那时还没有「当前对象」，硬塞进对话会绕。

### 四类对话流卡片

`ChatMessage.role` 增加 `'card'`，并加 `card` 字段。形状：

```ts
type ChatCardKind = '审计' | '纠正' | '结果' | '提议'

interface ChatCard {
  kind: ChatCardKind
  claimId?: string      // 审计 / 纠正 / 结果（关窗、晋升）
  proposalId?: string   // 提议
  briefId?: string      // 结果（简报出站）
  result?: '关窗' | '晋升' | '记忆' | '简报'
}

interface ChatMessage {
  id: string
  role: 'user' | 'desk' | 'card'
  text: string
  claimRefs?: string[]
  note?: string
  card?: ChatCard
}
```

**审计卡 `kind: '审计'`。** 点右栏投影里的一句、简报引用、或回复里的引用 chip，往当前对象对话流追加。字段搬原抽屉：正文、状态 / 未核 / 谓词槽、有效期、进料路径、来源标题、原文片段（高亮 span）、**冲突双方真并排**、接替主张跳转。动作行三个，同一层级次级样式（见 P2-3）：晋升、这句不对、看来源全文。

**纠正卡 `kind: '纠正'`。** 审计卡点「这句不对」，或对话里说「这句不对」且已有 `selectedClaimId` 时追加。关闭原因两个 chip 必选一个（不要原生 radio，见 P2-1），可选新主张 textarea，确认 / 取消。确认后走现有 `CORRECT_CLAIM`，再追加一张结果卡。

**结果卡 `kind: '结果'`。** 只读一行摘要 + 可点回引用。四个来源：关窗完成、晋升完成、记忆写入完成（替换现在的 `note`）、简报出站完成（点开切到右栏简报标签）。对话流因此是这个对象上的工作时间线。

**提议卡 `kind: '提议'`。** 待确认页每条加「在对话里处理」，把提议送进相关对象的对话流。待确认页保留为 backlog，两处都能决策，走同一个 `PROPOSAL_DECIDE`。

## P2 · 八条 UI 一致性

- **P2-1 原生 radio。** 纠正卡关闭原因不要 `<input type="radio">`。项目里二选 / 多选都是 chip 或方块按钮（谓词标签、主题方块、思考强度、绑定复选），跟着走。
- **P2-2 纠正区的危险红过度。** 纠正是关窗留档，不是删除（0006：账本旧句不动）。红框 + 红实心确认要降级：中性边框 + 主色确认。红色只留给「永久删除」那种真不可逆。
- **P2-3 动作权重反了。** 现在「晋升」是 primary 蓝、「纠正」是无样式默认按钮，纠正影响更大。审计卡上两个动作同一层级次级样式，谁都不抢。
- **P2-4 切对象会重置右栏。** `SET_VIEW` 把 `rightTabs` 清成只剩档案。改成按 `objectId` 记住已打开的标签与激活项。
- **P2-5 对话流式动画重放。** 切走再切回来，`ChatPane` 的 `seenIds` 被 `objectId` effect 清空，历史消息重放打字和工具行。改成按消息 id 全局去重，历史消息直接落定态。
- **P2-6 调试信息当标题。** 原抽屉头部把 `cl-3` 放最左。审计卡里 id 挪到底部，或只在悬停时显示。
- **P2-7 简报综合句被截断。** `brief.ts` 块四 `.slice(0, 40)` 截出半截句。改成按主张条目列举，别拼长句再截。
- **P2-8 「记下来」不去重。** 同一句写两遍得到两条一样的全局记忆。原型层做文本相等去重。真正的合并是 dream，不在这一刀。

## P3 · 三条覆盖缺口

- **P3-1 Inbox 没有进料入口。** 只能消费种子；新建工作区是死路。`prototype.md` 屏幕清单「空工作区 → Inbox 引导丢材料」没实现。做法：Inbox 顶部「粘贴文本 / 贴 URL」表单，写入 `sources`（`path: '手给'`，未绑定，带当前 `workspaceId`）。**不真解析 URL**，只存标题 + 正文，URL 形态标注「成品才抓」。
- **P3-2 历史简报不可达。** `BriefView` 的历史列表只在 `!embedded` 时渲染，右栏永远 embedded 且只取 latest。CONTEXT「同一对象可留多份历史简报」、0017「历史简报并排即 diff」没有界面。做法：右栏简报标签顶部加历史选择器（任务 id + 时间），能切回旧简报只读查看。
- **P3-3 任务实体完全缺失。** `State` 没有 `tasks[]`，`brief.taskId` 是现造字符串，调研和回放是 toast。0007 / 0016 / 0018 的任务层从没在界面上定过，下一刀（Electron + SQLite）第一件事就要建表。**这一刀只做最小一步：** 加 `tasks[]`（id、objectId、kind、状态、createdAt）；出简报时真建一条 `kind: '出简报'` 的任务，简报挂它的 id；右栏简报历史选择器按任务显示。调研与回放仍是「成品才跑」。任务的完整状态机是待拍板 §7，别自己定。

## 须主人拍板（不许自行决定）

这些会改数据语义或账本口径。执行者在相关代码留 `TODO(待拍板 §n)`，按现状原样运行。

1. **冲突谁来判、是存储还是派生。** 0003 说冲突是关系，0025 给了幂等键，但「取值互斥」由规则判还是模型判、冲突是存储的行还是每次查询派生，两处都没说。P0-1 用预置对绕过。
2. **未核被纠正也写全局禁写——这是设计缺陷，不是覆盖缺口。** 实测纠正一条未核的 Java 主张，除了关窗还往全局记忆塞一条永久禁写。0006 没区分「被纠正的是已晋升的定论」和「被纠正的是自动抽取的噪声」。丢一条噪声就污染记忆仓，正是 0022 自己引用过的 Mem0 放大路径（把已召回 / 已写入的再抽一遍会放大编造；此处是把未核噪声写成永久禁写，同型）。建议未核走丢弃 / 整理，纠正 + 禁写只留给已出站过的定论。本刀继续按现 reducer 写禁写，等拍板。
3. **「从未成立」要不要有效期。** 现在显示 `validFrom → validTo=今天`，读起来像「到今天为止是对的」。0006 引的 Wikidata：过时用 end time，从来不对用 deprecated rank 且不加结束时间。
4. **禁写的粒度。** 实现是 `memory.text.includes(claim.text)` 精确子串，只能拦一模一样的正文。Java 句从第二份简报消失的真正原因是 `status` 变成过时被过滤，禁写机制本身在主链里从未被检验。0010 的「纠正复发」指标目前没有可实现的定义。
5. **谓词槽是否绑定对象种类。** 原型硬编码 `SLOTS_BY_KIND`（人 = 任职于；组织 = 在招岗位 / 使用技术 / 办公地点 / 融资轮次；项目 = 在招岗位 / 使用技术），0025 只给了一份平表。「人」只有一个槽，周若水档案页基本空白——了解面试官是这个产品的一半场景，设计层就缺料。
6. **工作区的边界。** `Source` 带 `workspaceId`，Inbox 与待确认按当前区过滤，但两者挂在全局图标轨上，用户会以为看到了全部。`REMOVE_WORKSPACE` 之后区内对象被归档、`workspaceId` 仍指向已删除的区，于是它们在任何区都不可见、主张还在账本里——孤儿对象没有找回入口。0026 少一句话。
7. **任务的完整形态。** 四种任务谁创建、什么状态机、和简报什么关系、雷达在本机形态下应用没开时怎么算。P3-3 只做最小一步。
8. **CONTEXT 内部矛盾。** 主张状态列了「未知」，而「未知」词条说未知是材料不足时的合法结果（原型选择了「没有主张 = 空格子」）。那么 `status: '未知'` 的主张是什么？要么删掉这个状态，要么定义它（例如「来源明确表示不知道」）。「部分成立」同样没有判定规则、没有界面、原型零使用。
9. **对象同一性 / 别名。** 抽出的主张挂哪个对象，现在靠种子写死。真实第一刀就会撞上「JD 里提到的『栈桥』要不要建对象」。
