# 待确认写提议是账本状态，不是运行时 UI 状态

0028 把会改账本或记忆的动作收束到 takeover：模型或界面只能生成提议，使用者确认后才落账。M16 又让任务末批量晋升成为一条 takeover 提议。若这些提议只存在于主进程/renderer 内存，应用重启后会消失，使用者看到的“等待确认”就不是可恢复的业务事实。

StaffDesk 将 `writeQueue` 持久化进业务大脑文件的 `write_queue` 表。它保存待确认动作的最小执行载荷：对象、种类、标题、依据、相关主张/来源/任务、目标谓词与出站标记。`snapshot()` 从 SQLite 读取队列；`CONFIRM_WRITE` 和 `REJECT_WRITE` 按 `writeId` 删除对应行并追加结果卡。队列仍只表示“等待使用者确认的写动作”，不是操作日志；确认、拒绝、撤销这些已发生动作继续由 chat result card 与 operations 记录。

这意味着备份/恢复包含待确认写提议，因为它们属于当前大脑的业务上下文；但模型端点、密钥、资格认证仍按 0040/0048 留在产品级设置之外。运行中的抽取/导入作业仍保持运行时语义：重启后按既有中断规则处理，不与 `write_queue` 混为一谈。

实现上允许旧库无 `write_queue` 表时迁移创建空表；历史运行时队列本来不可恢复，不做追溯构造。
