# AI 能调的工具分三层；写账本只能提议，确认占用输入区而不是弹框

把人能做的操作原样开给模型，等于把账本的笔交给一个会幻觉的东西；只给只读工具又回到「参谋台只会答话」。中间那条路的风险不是权限，是确认疲劳：确认做成模态会打断阅读、做成流里的卡片会被后续消息滚走，两种都逼着人闭眼点通过，未核于是直接变定论（0005 最怕的退化）。业内可抄的形态是 composer takeover：deepseek-harness 的 ui-approval 把一个待批准请求坐到输入卡的位置，一次只处理一个，卡上有 warn 色等待条、要做什么的 headline、等宽字体的具体内容、右对齐的拒绝（outline）与允许一次（primary）；ui-user-questions 的反问用同一座位；「以后都允许」这种预设只存在于 ui-permission-presets，不进账本类操作。StaffDesk：工具按谁承担后果分三层。只读工具（召回主张、读来源片段、列冲突、读简报、查空槽）模型直接调，只在流里留一行工具行；会改账本或记忆的工具（绑定、晋升、纠正、接受整理、写记忆）模型只能产出提议，人确认才落，提议以 takeover 卡坐在输入区；不可逆或越界的（永久删除对象、移除工作区、改密钥、开深挖档）不给工具，模型最多在回答里建议人自己去做。约束：一次一件，且「一次」的判定键必须是提议自身的 id 而不是当前打开的对象——显示哪条与执行哪条必须是同一条，否则人在确认卡上看着 A 批准了 B，这正是本条要防的盲签；提议落在哪个对象由句子里指名的对象决定，指不出就不产提议，不得默默用当前打开的对象顶替；每张提议必须显示改什么与依据的主张或原文片段，无出处的写提议不许生成；账本写入没有全局「以后都允许」，晋升要人逐条负责；禁写是硬闸，除了拦简报出站也拦模型的提议；模型不得自开谓词槽（0025），编目只能提议并入现有槽；召回工具必须带工作区与对象作用域，不能绕过 0012 的未绑定不进语境。本条细化 0021 的四组工具与 0027 的卡片分工：审计卡与结果卡留在对话流（一个只读、一个已发生），纠正卡与提议卡搬到 takeover 座位。形态以 `prototype/` 为准。补记：手动绑定在 Inbox 确认、AI 提议绑定在 takeover 确认，是同一写入动作的两个人工入口（0012 的「建议对象须人确认」与这里的提议形态不冲突）；解绑可由 AI 提议、删除不给工具，见 0031。
